# Архитектура FlashTune

## Общая логика

Сайт должен работать как сервис подбора и продажи калибровок ЭБУ.

Пользователь может найти решение двумя путями.

### Вариант 1. По автомобилю

Пример:

`BMW → F30 → 320d → Bosch EDC17C50 → HW → SW → Stage 1`

### Вариант 2. По данным блока

Пример:

`Bosch → EDC17C50 → HW → SW → доступные калибровки`

Это особенно важно для профессиональных пользователей, которые уже знают идентификаторы блока.

## Основные части системы

### 1. WordPress

WordPress отвечает за:
- административную панель;
- страницы сайта;
- статьи и информационные материалы;
- меню;
- SEO;
- общую структуру сайта.

### 2. Кастомная тема FlashTune

Тема отвечает за внешний вид:
- главная страница;
- каталог;
- карточка калибровки;
- поиск;
- футер;
- личный кабинет;
- адаптивный дизайн.

Визуальный стиль:
- тёмный фон;
- неон;
- street racing;
- anime/cyberpunk;
- красный, голубой и фиолетовый акценты.

### 3. WooCommerce

WooCommerce отвечает за коммерческую часть:
- цена;
- корзина;
- заказ;
- оплата;
- статусы заказа;
- клиентский аккаунт;
- право на скачивание после оплаты.

### 4. Каталог Firmware

Для прошивок нужен отдельный тип записей или отдельная таблица.

Минимальные поля одной записи:
- `brand` — марка;
- `model` — модель;
- `generation` — поколение;
- `year` — год или диапазон лет;
- `engine` — двигатель;
- `ecu_vendor` — производитель блока;
- `ecu_model` — модель блока;
- `hw` — аппаратный номер;
- `sw` — программный номер;
- `calibration_type` — тип решения;
- `power_stock` — мощность в стоке;
- `power_tuned` — мощность после настройки;
- `torque_stock` — момент в стоке;
- `torque_tuned` — момент после настройки;
- `price` — цена;
- `storage_path` — путь к файлу;
- `status` — статус публикации.

### 5. Хранилище файлов

На первом этапе:

`VPS / private-firmware / ...`

Файлы нельзя хранить в обычной публичной папке WordPress `uploads`, если по прямой ссылке их сможет скачать любой человек.

WordPress должен проверять:
1. кто пользователь;
2. какой заказ был оплачен;
3. имеет ли пользователь право на скачивание;
4. какой именно файл ему разрешён.

Только после этого сервер отдаёт файл.

### 6. Оплата

Планируемая схема:

`Карточка калибровки → WooCommerce → платёжный шлюз → успешная оплата → заказ получает нужный статус → появляется доступ к файлу`

Рассматриваемые шлюзы:
- ЮKassa;
- PayKeeper.

### 7. Индивидуальные заказы

Если готового решения нет:

`Пользователь → загружает оригинальный BIN → создаётся заказ → специалист обрабатывает файл → готовый файл прикрепляется к заказу → клиент скачивает результат`

Позже это можно частично автоматизировать.

### 8. Массовый импорт

10 000–50 000 записей нельзя создавать вручную.

Нужен импорт из CSV/Excel или из существующей структуры папок.

Пример CSV:

`brand,model,engine,ecu_vendor,ecu_model,hw,sw,calibration_type,price,storage_path`

Импортёр должен:
- проверять данные;
- создавать записи;
- обновлять существующие;
- не создавать дубликаты;
- связывать записи с файлами.

### 9. GitHub Pages

GitHub Pages используется только для статического preview.

Production-WordPress будет работать на VPS или обычном WordPress-хостинге.
